# Agent Prompt 精修（二）设计

> 2026-05-27 — 在现有结构内继续精修三类输出：六部复奏、内阁复奏、大学士廷议。

## 背景

上一轮已经完成了共享边界、角色职责和基础模板的重构，但还有三处输出仍然偏“通用框架”，没有充分体现角色差异：

1. 六部虽然已有专属规则，但 `【本部复奏】` 仍缺少更明确的部门化交付字段。
2. `【内阁复奏】` 还偏简短结案，尚未形成偏技术总监风格的状态汇报。
3. 三位大学士虽然有审议侧重，但输出骨架仍较接近，廷议结果仍可能结构同质化。

本轮不调整 agent 架构，不新增文件，不拆新的 prompt 系统，只在现有 `src/prompts.ts` 与少量 markdown 文案中做小范围精修。

## 目标

1. 让六部复奏更像各自专业产物，而不是同一张空表。
2. 让内阁复奏更像复杂任务的技术总监式状态汇报。
3. 让大学士廷议在结构上更稳定地输出差异化视角。

## 方案

### 六部复奏精修

保留统一的 `MINISTRY_FORM`，但在 `MINISTRY_RULES` 中要求各部复奏必须附带特定信息：

- 吏部：执行方案、职责分配、验收标准、交接边界
- 户部：相关文件、依赖关系、调用链、未确认点
- 礼部：歧义点、规范建议、文案或交互修订
- 兵部：执行顺序、并发策略、失败重试、回滚条件
- 刑部：是否准行、问题严重性、缺失验证、封驳点
- 工部：改动文件、验证结果、剩余风险、未完成项

### 内阁复奏精修

将 `【内阁复奏】` 调整为偏技术总监的状态汇报模板，字段聚焦：

- 当前结论
- 已办事项
- 关键证据
- 阻塞与未决
- 风险与影响面
- 下一步建议
- 请陛下裁定

### 大学士廷议精修

保留共同骨架，但要求输出必须显式包含：

- 你的判断
- 建议方案
- 主要风险
- 需圣裁事项
- 与常规看法不同之处

再叠加三位大学士的固定审议侧重：

- 甲：完整性、长期维护、边界覆盖
- 乙：实现成本、交付节奏、复杂度控制
- 丙：反例、失败路径、回滚与最坏情况
