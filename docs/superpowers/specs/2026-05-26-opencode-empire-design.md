# opencode-empire 设计规格

日期：2026-05-26
状态：已完成设计草案，待用户最终审阅

## 1. 背景与目标

`opencode-empire` 是一个 OpenCode 多智能体编排插件。它借用“皇帝、内阁、六部”的组织隐喻，把复杂开发任务从“直接执行”改造成一套可审议、可批红、可派工、可复奏的协作流程。

第一版目标不是做完全自动化代理系统，而是实现一个可靠的半自动编排体验：

- 用户作为“皇帝”，提出意图、批红确认、裁决分歧。
- `empire-cabinet` 作为“内阁”主 agent，负责自然对话入口、需求澄清、廷议、票拟、派工建议和复奏。
- 三位隐藏“内阁大学士”由不同模型驱动，负责同职独立审议。
- 六部作为可见子代理，分别承担执行方案、代码探索、方案审核、执行自动化、代码审查、代码实现。

第一版成功标准：用户选择 `empire-cabinet` 后，可以通过自然对话进入“票拟 -> 批红 -> 派工 -> 办理 -> 复奏”流程；命令入口可用于强制进入或纠偏；六部职责清晰；未批红前不会自动进入执行。

## 2. 产品原则

1. 内阁是正门。用户主要和 `empire-cabinet` 对话，由内阁判断是否进入票拟或派工流程。
2. 角色要入戏，但工程信息必须清楚。输出采用中度角色化语气，文件、命令、风险、测试和验收标准必须直接明确。
3. 半自动优先。内阁可以建议派工，但重要执行步骤必须等用户批红。
4. 共识优先。三位大学士独立审议后，由内阁先呈共识，再呈分歧和待裁决事项。
5. 第一版保持低侵入。优先使用 OpenCode 插件配置、agent 注册和 system prompt 注入，不做复杂 runtime 拦截。

## 3. 角色体系

### 3.1 皇帝

用户即皇帝，负责：

- 降旨：提出需求或任务。
- 批红：确认票拟、派工单或关键修改。
- 圣裁：决定内阁无法自行合并的分歧。
- 驳回：要求重拟、缩小范围或改变方向。

插件应减少用户处理噪音，只把需要决策的事项呈上来。

### 3.2 内阁

`empire-cabinet` 是可见主 agent，也是默认交互入口。

职责：

- 听旨：理解用户需求，判断普通答复还是进入流程。
- 追问：需求边界不清时，一次只问一个关键问题。
- 廷议：调用三位隐藏大学士独立审议。
- 票拟：整合共识、分歧、风险、验收标准和派工建议。
- 请批红：等待用户确认、修改或驳回。
- 发部：根据已批票拟生成六部派工建议。
- 复奏：汇总办理结果、证据、风险和下一步。

内阁不直接负责代码修改。代码修改由工部办理，代码审查由刑部办理。

### 3.3 三位内阁大学士

三位大学士是隐藏 subagent：

- `empire-grand-secretary-a`
- `empire-grand-secretary-b`
- `empire-grand-secretary-c`

三者职责相同，模型不同，独立审议同一需求。它们用于发现不同模型视角下的理解差异、风险、方案取舍和待确认事项。

大学士不直接面向用户，不直接修改代码，不直接派工。它们的输出由内阁整理成“共识优先”的票拟。

### 3.4 六部

六部是可见 subagent，可以由内阁建议调用，也可以被用户直接点名。

| Agent | 官署 | 职责 |
| --- | --- | --- |
| `empire-ministry-personnel` | 吏部 | 执行方案 |
| `empire-ministry-revenue` | 户部 | 代码探索 |
| `empire-ministry-rites` | 礼部 | 方案审核与交互文案 |
| `empire-ministry-war` | 兵部 | 执行与自动化 |
| `empire-ministry-justice` | 刑部 | 代码审查与测试把关 |
| `empire-ministry-works` | 工部 | 代码实现 |

六部具体职责：

- 吏部：将已批红票拟转为具体执行方案，包括任务拆分、执行顺序、职责边界、派工单、验收标准、回滚路径。
- 户部：读仓库、查文件、梳理现有架构、识别依赖、定位相关模块，呈报“代码舆图”。
- 礼部：审核执行方案是否符合批红范围、用户体验、角色口吻、命令命名和说明文档表达。
- 兵部：负责任务派发、并发执行、命令流程、失败重试和自动化协同。
- 刑部：审查实现质量、风险、权限、安全、边界条件、测试覆盖，给出准行、驳回、补测或重构建议。
- 工部：负责实际代码修改、插件实现、构建配置、类型修复和集成落地。

## 4. 工作流

核心链路：

```text
皇帝降旨 -> 内阁听旨/追问 -> 三位大学士廷议 -> 内阁票拟 -> 皇帝批红
-> 吏部拟执行方案 -> 礼部审核方案 -> 六部办理 -> 刑部审查代码 -> 内阁复奏
```

状态流：

```text
听旨 -> 追问 -> 廷议 -> 票拟 -> 待批红 -> 拟派工 -> 待发部 -> 办理中 -> 复奏
```

状态说明：

- 听旨：内阁判断是否需要进入流程。
- 追问：需求不清时，一次只问一个关键问题。
- 廷议：三位隐藏大学士独立审议。
- 票拟：内阁整合共识、分歧、风险和建议。
- 待批红：等待用户确认、修改或驳回。
- 拟派工：吏部把已批票拟转成执行方案，礼部审核方案。
- 待发部：内阁呈上六部派工单，等用户确认。
- 办理中：六部按职责执行。
- 复奏：内阁汇总结果、证据、风险和下一步。

## 5. 入口与命令

第一版以自然对话为主，命令为辅。

自然对话示例：

- “让内阁先票拟一下。”
- “交六部办理。”
- “请刑部审一下代码。”
- “这个方案驳回，重拟。”

命令入口：

- `/票拟`：强制进入需求澄清和票拟。
- `/廷议`：请三位大学士独立审议。
- `/批红`：确认某版票拟或派工单。
- `/驳回`：要求重拟或指出修改方向。
- `/发部`：根据已批票拟生成六部派工建议。
- `/复奏`：汇总当前办理结果。

命令用于显式触发、流程跳转和纠偏。自然对话仍是主路径。

## 6. 文书格式

### 6.1 内阁票拟

```text
【内阁票拟】
臣等共识：
尚需圣裁：
拟行方案：
不办事项：
风险与封驳点：
验收标准：
建议派工：
```

### 6.2 六部派工单

```text
【六部派工单】
批红依据：
本轮目标：
各部职责：
执行顺序：
需调用模型：
验收凭据：
回滚方案：
请陛下批红：
```

### 6.3 内阁复奏

```text
【内阁复奏】
已办：
证据：
未决：
风险：
请陛下裁定：
```

### 6.4 六部复奏

```text
【某部复奏】
臣等所办：
证据：
所遇风险：
请陛下裁定：
```

文书可以有角色化措辞，但必须保留明确字段，便于用户审阅，也便于后续流程续接。

## 7. 模型策略

模型策略采用混合方式：

- 每个角色有默认模型。
- 三位大学士默认绑定三个不同模型，以保证独立审议视角。
- 六部有各自默认模型，例如代码实现和代码审查可使用更强模型，代码探索和文档可使用较快模型。
- 内阁可以在派工单中建议临时升格或降格某个任务模型。

配置应允许用户覆盖：

- 三位大学士的模型。
- 六部默认模型。
- 是否启用特定部门。
- 角色语气强度。
- 是否要求每次发部前显式确认。

第一版默认要求发部前显式确认。

## 8. OpenCode 插件结构

第一版采用：

- 可见主 agent：`empire-cabinet`
- 隐藏内阁大学士：`empire-grand-secretary-a/b/c`
- 可见六部：`empire-ministry-*`
- 插件命令入口：`/票拟`、`/廷议`、`/批红`、`/驳回`、`/发部`、`/复奏`
- system prompt 注入：让内阁理解流程、角色、状态、文书格式和权限边界

实现上优先使用 OpenCode 插件的 agent/config 能力。第一版不依赖复杂 runtime Task 拦截，也不要求插件自动改写每一次工具调用。

## 9. 错误处理

默认原则：不确定时停下来复奏，不继续猜。

- 需求不清：回到追问，不进入票拟。
- 三位大学士意见冲突大：列为“尚需圣裁”，不强行合并。
- 执行方案越过批红范围：礼部驳回，要求吏部重拟。
- 代码探索证据不足：户部补查，不让工部盲改。
- 实现失败或测试失败：工部或刑部呈报失败证据，内阁请用户裁定下一步。
- 涉及破坏性命令、外部网络、密钥、生产数据：必须显式请旨。

## 10. 权限边界

- 内阁可以建议、整理、派工和复奏，但不应绕过用户批红直接进入大范围执行。
- 三位大学士只参与廷议，不直接改代码。
- 吏部负责执行方案，不直接改代码。
- 户部只探索代码，不修改代码。
- 礼部审核方案、交互和文案，不负责代码质量终审。
- 兵部负责执行流程和自动化，但不能绕开内阁批红链路。
- 刑部负责代码审查和测试把关，默认不直接修代码。
- 工部负责代码实现，必须依据已批派工单。

## 11. 测试策略

第一版测试分三层：

1. 配置测试：验证插件能注册内阁、隐藏大学士、可见六部，模型配置可覆盖。
2. 提示词和文书测试：用样例输入检查内阁是否输出票拟、派工单、复奏，并包含必要字段。
3. 流程测试：模拟“需求 -> 票拟 -> 批红 -> 派工 -> 复奏”的会话，确保不会在未批红时发部办理。

验收标准：

- 安装插件后，用户可以选择 `empire-cabinet` 对话。
- 自然对话能进入票拟流程。
- 三位大学士不出现在常规 agent 列表。
- 六部可见且职责清晰。
- 命令入口可强制进入对应阶段。
- 未批红前不会自动发部办理。
- 代码实现由工部负责，代码审查由刑部负责。

## 12. 第一版不做事项

- 不做完全自动连续执行。
- 不做复杂长期记忆或跨项目治理。
- 不做多轮派工的数据库级状态机。
- 不做任意 Task 调用的 runtime 强拦截。
- 不把古风表达置于工程清晰度之上。
